## 1. 現状フローの要約

観察されたフローは以下の通りです。

1. `prompts/phase-X/NN-task.md` に**詳細なタスクプロンプト**を人手で作成（多くが完成コード付き）
2. AI（Codex / Claude Code）がプロンプト通りに実装
3. `npm run dev` で表示 → **スクリーンショットを目視**で確認
4. 不具合が出たら **修正プロンプト（03b / 03c / 05b …）を追加**して再実装
5. `git commit`（メッセージは「修正」「実装」等の短文）→ `main` に直接積む

---

## 2. 良い点（維持すべき運用）

- ✅ **プロンプト駆動**でタスクが文書として残り、履歴を追える
- ✅ 各プロンプトに **「制約」「確認手順」** セクションがあり、成功条件が明文化されている
- ✅ AGENTS.md が Single Source of Truth として機能し、規約が一元化されている
- ✅ 「変更しないファイル」をプロンプトで明示 → スコープ管理の意識が高い

## 3. 問題点（証拠付き）

| # | 問題 | 証拠 | 影響 |
|---|---|---|---|
| P1 | **修正プロンプトの多発（fixスパイラル）** | phase-5 だけで 03b/03c/05b/05c/06b/06c と**7本の修正プロンプト** | 1タスク=2〜3往復。レビュー工数が肥大 |
| P2 | **自動品質ゲートが無い** | `package.json` の scripts は dev/build/start/lint のみ。**typecheck 無し**、コミット前チェック無し | 型エラー・ロジック反転が目視レビューまで残る |
| P3 | **バグ検出が目視スクショ頼み** | 各プロンプトの確認手順が全て人間の目視。例: 06b の「ピンのアクティブ判定が逆」は実装後に発覚 | 発見が遅く、手戻りが大きい |
| P4 | **コミット粒度・メッセージが粗い** | 「修正」「背景」「もろもろ更新」、235文字の巨大コミット1件。未コミット変更が **18ファイル + 未追跡多数** | 差分レビュー・ロールバックが困難 |
| P5 | **main 直コミット / PR未使用** | ブランチ `claude/adoring-thompson-03ad9d` は存在するが実運用は `main` 直 | 差分単位のレビュー機会が無い |
| P6 | **プロンプトに完成コードを全書き** | 200〜474行のプロンプトが多数（13番は459行、phase5-task01は474行） | 作成コストが高く、AIの解決力を活かせず、統合バグを生みやすい |

## 4. 改善提案（優先度順）

### 🥇 優先度 高 — 「レビュー前の自動ゲート」を作る（P2・P3対策）

- [ ] **typecheck スクリプトを追加**（`tsc --noEmit`）し、AI が実装完了を報告する前に必ず実行させる
- [ ] **完了報告の定型化**: 「lint OK / typecheck OK / build OK」を報告に含めない限り「完了」と言わせない
- [ ] これだけで P1 のfixスパイラルの相当数（型ミス・未使用・null系）が目視前に潰れる

> 効果: レビューは「機械が通したものだけを見る」状態になり、人間は**ロジックと見た目に集中**できる。

### 🥈 優先度 中 — 「セルフ検証」をプロンプトに組み込む（P1・P3対策）

- [ ] 各プロンプトに **「セルフ検証」節** を追加。特に方向・順序・境界（例: `< 0.5` の向き、アクティブ判定）は**一時ログで実値を確認 → 削除**まで1往復に含める
- [ ] 「実装 → 自己レビュー（制約リストと突合）→ 報告」を1タスクの標準サイクルにする
- [ ] 06b のような**左右反転バグは、実装者自身が値を1回出せば初回で気づける**

### 🥉 優先度 中 — コミット/ブランチ運用の是正（P4・P5対策）

- [ ] **1タスク = 1コミット**、メッセージは `Phase5-06: エリア自動切替` 形式で統一
- [ ] 未コミット変更を溜めない（現在18ファイル滞留 → タスク完了ごとに切る）
- [ ] タスクごとに**作業ブランチ → 差分レビュー → main** の流れにする（ソロでも `git diff main...` でレビューしやすい）

### 優先度 低 — プロンプトのスリム化（P6対策）

- [ ] 完成コード全書きをやめ、**「意図 + 制約 + 受け入れ条件 + API/型の契約だけ」**に絞る
- [ ] コードブロックは「守ってほしい正確な型・関数シグネチャ」に限定し、実装本体はAIに委ねる
- [ ] 作成コストが下がり、AIの統合判断が働くことで逆に手戻りが減る

## 5. 推奨する「1タスクの標準サイクル」

```
1. プロンプト作成（意図・制約・受け入れ条件・型契約）
2. 作業ブランチ作成         git switch -c task/phase5-07
3. AI 実装
4. セルフ検証               境界/方向/順序を一時ログで確認 → 削除
5. 自動ゲート               lint → typecheck → build を全て緑に
6. スクショ確認             確認手順に沿って目視
7. 1タスク=1コミット        "Phase5-07: <要約>"
8. 差分レビュー → main マージ
```

## 6. レビュー効率化チェックリスト（コピペ用）

実装完了報告に、以下を貼らせると人間側のレビューが最短になります。

```md
## 完了報告
- [ ] 対象ファイル: （変更した全ファイルを列挙）
- [ ] 制約遵守: プロンプトの「制約」を1項目ずつ ✅/該当なし で回答
- [ ] npm run lint       → 結果を貼付
- [ ] npm run typecheck  → 結果を貼付（※要スクリプト追加）
- [ ] npm run build      → 成功/失敗
- [ ] セルフ検証: 境界・方向・順序の実値確認（ログ添付→削除済み）
- [ ] スクショ: 確認手順の各番号に対応する画像
- [ ] 未実装/ハック/TODO: 正直に列挙
```
